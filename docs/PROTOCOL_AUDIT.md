# Revit MCP 0.17.0 protocol and systems audit

**25 November 2026. Release verdict: hold the distributable.** The patched source is suitable for controlled testing. The public interface uses MCP over stdio. The add-in uses a separate, authenticated, newline-framed loopback protocol. A passing Python smoke test exercises the first interface against a simulated second interface. It cannot establish native Revit transaction behavior.

## Findings by severity

Severity reflects the potential consequence in the local Windows deployment. “Fixed” means the workspace contains the correction. The verification section identifies the checks that actually ran.

### Critical

No confirmed critical finding in the examined paths.

### High

| Category and source location | Defect and consequence | Disposition and concrete fix |
| --- | --- | --- |
| Input validation · `server/server.py`, tool envelopes, `_dispatch` and `revit_edit`; `plugin/Edit/EditEngine.cs`, `Run`; `ManageOps.Purge` | The SDK could discard unknown tool arguments. The edit handler ignored misspelled batch options, and null preview flags selected the commit default. Purge ignored unknown keep or category options. The Excel branch also silently won when both input modes were supplied. An edit accepted after permission could consequently commit or purge more than requested. | **Fixed for these paths.** Validate the actual envelope against the published schema before SDK conversion. Reject unknown batch and workbook edit options, misplaced preview flags, ambiguous split inputs and null or unrecognized purge options. Validate the batch at the native boundary too. Other individual operations still use their own accessors and do not universally reject unused keys. |
| Wrong target · `tests/live_p89.py`, initial project check and `call` | The scratch harness verified a project once, then resolved the active session and document again on subsequent edits. Changing documents could invalidate the original safety check. The harness also used a developer desktop export directory with overwrite enabled. | **Fixed.** Pin the connection, attach the checked document ID to every call, and use a unique temporary export directory. Failed post-commit work now fails the test, and failed checks produce a nonzero exit. |
| Retry semantics · `plugin/Bridge/EditReceipts.cs`, `Run`, `Rerunnable` and `Finish` | All escaping exceptions became retryable even after dispatch. The receipt layer had no evidence that every model or file effect had rolled back. This was an unsafe retry guarantee. No duplicated live edit was observed in this audit. | **Fixed.** Retain a terminal unknown-outcome receipt after an unhandled exception during execution. Only pre-dispatch failures and permission-pending attempts retain their retry behavior. The client carries the operation and process IDs on an unknown outcome. Bound reserved IDs to 65,536 per process and refuse new IDs when full, preserving existing deduplication. |
| Cancellation · `server/server.py`, `_run`; `server/excel_io.py`, batch loop; `xlsx_util.save_workbook` | Abandoning an AnyIO worker on cancellation left its workflow running. A later batch could start or a file could be published after cancellation. | **Fixed at dispatch and publication boundaries.** Share a per-request cancellation event with the worker and check before bridge sends, selection changes and workbook publication. An already-dispatched native operation can finish. Cancellation cannot atomically recall a socket send or file rename already underway. |
| Publication race · `plugin/Edit/EditContext.cs`, `GuardOverwrite`; `plugin/Edit/ExportOps.cs`, deferred exports | The add-in checks destinations before commit and hands the destination to the exporter later. Another process can create a file in between. An overwrite depends on the individual exporter. Multi-file exporters can leave partial output after a later file fails. | **Open.** Stage each export in its own directory, enumerate actual outputs and publish with filesystem-enforced no-replace semantics. Specify recovery for partially published multi-file sets. Exercise DWF, DWG and single-file exporters in Revit before changing this shared path. |

| Framing and cleanup · `BridgeServer.HandleClient`, `ReadLine`; `App.OnStartup`; `bridge_client.call`; `plugin/Core/Json.cs` | EOF could dispatch a final unterminated request. | Operational evidence · `plugin/Core/Audit.cs`, `Write` | Multiple Revit processes rotate and append to the same file. Rotation and append are separate operations. ## Lifecycle and transport evidence

A separate subprocess test negotiated MCP 2025-11-25, sent the initialized notification, received the expected numeric ping ID and string initialization ID, discovered the tool capability and schema, received a protocol error for an unknown tool, and exited cleanly on stdin EOF. No extra stdout appeared. SDK diagnostics went to stderr. The tested server starts only stdio. HTTP sessions, SSE reconnects and Origin handling are outside this entry point. [Lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle) · [Transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

SDK 1.30.0 owns version negotiation, JSON-RPC IDs and notification dispatch. Its `ServerSession._received_request` sets the initialized state after the initialize response. Its notification handler also sets that state on receiving the initialized notification. Consequently the SDK state alone cannot prove both messages occurred in order. This is a dependency-level observation. The client is responsible for sending the sequence. No application-generated pre-initialization request or notification feedback loop was identified.

The private bridge binds to loopback, generates a per-process token and checks it before dispatch. Connection metadata contains the token in a per-user file. Effective Windows ACLs, deployed binaries, external add-ins and client approval settings were outside the verification. Absolute workbook paths and named output folders are intentional local file capabilities. No SQL execution, shell execution from the dispatch handler or confirmed prompt-injection execution path was identified in the examined request flow.

## Redundancies and cleanup opportunities

* Move workbook table presentation out of `qs_report._table` into the shared workbook module. The BBS report currently imports a private helper and constants from the QS report.
* Define action fields, aliases and validators together, then generate documentation and machine-readable action schemas. The outer MCP envelopes are validated, while much of the per-operation catalogue is still free-form descriptive text. Preserve documented aliases and support for old workbooks before introducing strict validation across all 118 operations.
* Separate discovery, workflow coordination and MCP registration in `server/server.py`. Keep the snapshot of session selection at the start of a workflow. The architecture supports one client process per stdio server and would need per-session state if a shared HTTP transport were added.

## Verification boundary

The smoke suite covers real SDK stdio round trips with fake add-ins, two Revit processes, tool errors, permission and retry paths, workbook workflows, and catalogue consistency. Both add-in targets compiled. The bar-stock tests and temporary-directory installation, rollback and retry tests passed. These checks did not load the patched DLLs into Revit, exercise all 118 operations, reproduce native process races, or validate the frozen executable and installer. Earlier purge tests on 0.13.3 do not establish those outcomes for this revision.
